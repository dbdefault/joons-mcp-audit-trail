# Security

This tool detects modification; it does not prevent it. An attacker who can rewrite the log and has the key, or can recompute hashes in unkeyed mode, can forge a log. Tail truncation is detected only against an anchor or a known count. Timestamps are caller-supplied claims, not trusted time. It does not authenticate who wrote a record and is not a replacement for write-once storage.

Without a key or an anchor, a plain-looking rewrite of a log cannot be told from a genuine plain log: `verify` holds a log to the mode that its own header declares. Keyed mode protects you only if you verify with the key. Use `verify --key-file KEY --require-keyed` (or compare against an anchor kept elsewhere) so that a keyed log rewritten as a plain log is reported as `key_mismatch` with detail `header_not_keyed`.

## Threat model

What the tool is for: finding out afterwards that a log file was edited, that records were removed from the middle, inserted or reordered, or, with an anchor, that the newest records were cut off.

What it relies on: the head hash or anchor you kept, and in keyed mode the secrecy of the key file and the habit of verifying with it. Keep anchors where the log's writer cannot change them, and keep key files away from the log and from exports.

What it does not cover:

- An attacker with write access to the log and the key can build a new, valid keyed chain. In plain mode no secret is involved, so anyone can recompute every hash after an edit, and the result is a valid plain log.
- Downgrade: an attacker without the key can rewrite a keyed log as a plain log with a recomputed chain. That is caught when you verify with the key (or with `--require-keyed`) or against a keyed anchor, and not otherwise.
- A caller can submit false event data or a false time. The tool does not check either, and it does not authenticate the actor. A far-future explicit time on the newest record makes later default-clock appends carry that time (the clock is clamped to the newest record), and it blocks later appends with an earlier explicit time.
- Without an anchor or a known record count, removal of the newest records cannot be seen. An anchor stored next to the log can be replaced together with it.
- It is not write-once storage. The file can still be deleted or replaced; the tool only helps you notice that its content changed.
- `show`, `summary` and `export` do not verify hashes (they do require well-formed canonical lines). Only `verify` checks the chain.

## Credentials

`append` refuses values that look like common credential formats. The scan is a heuristic: it can miss secrets, including transformed, split or encoded ones, and it can refuse harmless text. A prefix family must start a token (a letter, digit, `_` or `-` before it means it is part of a longer word), so a key embedded in a longer word is not seen. Never put secrets or personal data in records. Exports and terminal output contain what the log contains.

## Keys and files

- A key file holds at least 16 bytes and at most 4 KiB; exactly one trailing line terminator (`\n` or `\r\n`) is removed, and a file of only line terminators is refused. It must be a regular file. There is no entropy check: a weak key is accepted. Only a key identifier (derived by hashing the key twice) is written to logs and anchors; it is identical in every log that uses the same key, so it links such logs and gives an offline oracle for guessing a weak key.
- The key never appears in output, error lines or exceptions. Error lines are a fixed kind with no path or content.
- One path checker covers the log, `--out`, `--key-file`, `--data` and `--anchor`: UNC and device-namespace paths in any slash or backslash mixture, NUL bytes, alternate data streams, Windows device names (`CON`, `NUL`, `COM1`, `COM` and `LPT` with superscript digits, `CLOCK$` and so on, with or without an extension) and names ending in a dot or space are refused on every platform, and on Windows a `~` followed by a digit in the log name (8.3 alias) is refused. Existing input files must be regular files with one hard link, checked before opening, so named pipes, sockets and devices are never opened. Symbolic links are refused.
- Parent directory components are not checked: a log below a symlinked or junctioned directory is accepted, and the lock file is derived from the real path of the parent to keep concurrent appends consistent. Still protect the containing directory with operating-system permissions.
- Output files for `anchor` and `export` are written through a temporary file in the same directory and are never overwritten without `--force`. An output that is the same file as the log, the key file or another input is refused even with `--force`, and so is an output that is a lock file: the name lock or the identity lock of an input, any name of the form `.audit-id-<hex>.lock`, and any existing file whose name ends in `.lock` (a held lock is never replaced). A killed process can leave a stale `.name.<hex>.tmp` file next to the target; it can be deleted by hand. The exclusive create uses `fs.link`, which needs a filesystem with hard links.
- `append` also takes a second lock named from the log file's device and inode numbers (a hidden `.audit-id-<hex>.lock` file next to the log), and the first lock's name uses the Unicode-normalized, case-folded file name where file names ignore case, so that two spellings of one file cannot write at the same time. A stale lock of either kind is handled like a stale lock below.
- `append` holds a lock file while it works. The file contains a random token (no secrets) and is removed only while it still holds that token; a missing file at cleanup is tolerated. A lock left by a killed process is not removed automatically. After a kill both the name lock (`<log>.lock`) and the identity lock (`.audit-id-<hex>.lock`) can remain, and the operator must delete both (only after confirming that no writer is running); deleting only one still gives `lock_timeout`. A log named `x.lock` blocks appends to `x`. An unfinished or non-canonical last line blocks further appends until you investigate; the tool never repairs a log.
- `actor`, `tool` and `type` refuse non-ASCII spaces, default-ignorable and unassigned code points, so look-alike names cannot be created; `actor` and `tool` also refuse the literal `(other)` and a leading or trailing space. These rules apply when writing (the unassigned rule follows the Unicode data of the running Node.js); the stored-name check (`verify` and the tail check of `append`) uses a fixed, version-independent table of explicit stable classes that is a subset of what the writer rejects (it holds no visible punctuation, symbol, letter, mark or number; see LIMITATIONS.md) and does not apply the `(other)` and space rules, while `show`, `summary` and `export` check key set and canonical form and sanitize output, so logs stay verifiable across Node.js versions. `--data` files with a duplicate key at any depth are refused. The log format is strict: every stored line must equal the canonical form of its record, so re-spelled lines (whitespace, key order, duplicate keys, escapes, number spellings, byte-order mark, padding) are reported even if the hashes match.
- Terminal output replaces every default-ignorable, format (Cf), control (Cc), private-use (Co), surrogate (Cs) and unassigned (Cn) code point, the 22 format characters U+110BD, U+110CD, U+13430 to U+1343F and U+1BCA0 to U+1BCA3, the older explicit list and every non-ASCII space separator (U+00A0, U+1680, U+2000 to U+200A, U+202F, U+205F, U+3000) with `?`. JSON output escapes DEL and the C1 controls as `\u00XX` and otherwise follows the JSON rules. Markdown output writes every cell as one inline code span, so markup, links, bare URLs and e-mail addresses are not interpreted. CSV cells are sanitized with the same rule in every column: each code point that the terminal replaces (C0 and C1 controls, DEL, non-ASCII spaces, U+2028, U+2029, U+2800, U+FFFC, invisible, bidirectional, private-use and unassigned code points) is written as `\uXXXX` text. Terminal output merges names and keys that differ only by replaced characters into one entry (JSON and exports stay exact), and JSON output passes bidirectional and other format characters through raw by design. CSV cells that could be read as spreadsheet formulas get a leading `'`: control characters (tab, CR, LF) are escaped as `\u00XX` before the formula guard looks at the cell, so the guard applies after leading spaces only.
- The tool makes no network connections, starts no subprocesses, evaluates no code, reads no environment variables and sends no telemetry.

## Reporting a vulnerability

Please report a suspected vulnerability privately through the repository's private vulnerability reporting, when it is enabled, or otherwise by contacting the maintainer through the repository profile. Include the version, a minimal reproduction without real credentials, the impact and your environment. Please allow reasonable time to investigate before publishing details.
