# Limitations

This tool detects modification; it does not prevent it. An attacker who can rewrite the log and has the key, or can recompute hashes in unkeyed mode, can forge a log. Tail truncation is detected only against an anchor or a known count. Timestamps are caller-supplied claims, not trusted time. It does not authenticate who wrote a record and is not a replacement for write-once storage.

Without a key or an anchor, a plain-looking rewrite of a log cannot be told from a genuine plain log. If you rely on keyed mode, verify with `--key-file` and `--require-keyed`.

## Known limits

- A plain chain has no secret. Whoever can write the file can recompute it; custody of an independent anchor matters. A keyed log that is rewritten as a plain log verifies as a plain log unless you give the key (or require it) or compare with a keyed anchor.
- A keyed chain is only as safe as its key. Losing the key makes the keyed hashes unverifiable. The tool does not check key entropy, and the key identifier stored in every header and anchor is the same for every log that uses the key: it links such logs and lets anyone holding a log test guesses offline. It does not manage key rotation, escrow or identity; start a new log to change keys.
- An anchor is a snapshot: it detects removal or rewriting of anything up to its count, not changes after it, and a longer valid log still matches an old anchor. An anchor stored next to the log protects little. Cutting a log at a record boundary without an anchor is not detectable.
- Time is whatever the caller passes. Times may repeat and `append` refuses an explicit time earlier than the last record, but the tool does not know the real time. The default clock is clamped to the last record, so a backwards clock step or a far-future time on the last record makes later default-clock records carry that time, and a far-future time blocks later explicit times that are earlier.
- `append` checks only the header and the last record, not the whole chain. Only `verify` checks everything. `show`, `summary` and `export` require well-formed canonical lines but do not check hashes.
- Credential refusal is heuristic. It cannot find every credential or transformed secret, it only sees a prefix family at the start of a token, and it may refuse harmless text.
- A log can hold sensitive data, and exports and terminal output show it. Sanitized terminal output is not redaction.
- Limits fail closed: 65,536 bytes per line, 256 MiB per log, 1,000,000 records, 32 KiB of data per event, depth 6, 64 keys per object, 64 elements per array, 4,096 characters per string, 10,000 records and 16 MiB of rendered output (counting every byte, the closing tail included) per `show`, 10,000 distinct names of at most 128 code points per summary field, 16 MiB of rendered `summary --details` output. Event data allows only safe integers, read by value (`1.0` and `1e2` are accepted and stored as `1` and `100`; `1.5` is refused). A `--data` file above 32 KiB is `limit_exceeded`; a smaller file whose canonical form is above 32 KiB (`1e9` becomes `1000000000`) is `invalid_record`. A log with more than 1,000,000 lines is `limit_exceeded` for the readers and a set of findings for `verify`.
- The last line must be complete and canonical. A line that is cut off, stale lock files, a stale `.name.<hex>.tmp` file left by a killed `anchor` or `export`, and a damaged log are not repaired automatically. After a kill both `<log>.lock` and `.audit-id-<hex>.lock` can remain, and both must be deleted by the operator (deleting one is not enough) once no writer is active.
- A log whose own name ends in `.lock` (for example `x.lock`) blocks appends to `x`, because `x.lock` is the lock name of `x`. `anchor` and `export` refuse an `--out` that is a lock file.
- `show` with both `--from` and `--to` given and a range wider than 10,000 records is a usage error (exit 3). With only `--to`, only `--from` or neither, a selection of more than 10,000 records (for example the default range over a log with more records) is `limit_exceeded` (exit 2).
- `anchor --out y.lock` or `export --out y.lock` on a log other than `y` is accepted when `y.lock` does not exist, and the new file then blocks appends to the log `y` with `lock_timeout` (the refusal of an existing `.lock` file covers files that already exist).
- An existing file whose name ends in `.lock` can never be overwritten with `--out --force` (a safety rule, kept even for an old export); remove it first.
- Non-string values in a forged log (an actor `[1]`, a number) and the literal name `(other)` are counted under `(other)` in the summary, never under their own names.
- `append` prints its result after the record is durable. If writing that result fails (a closed pipe), the exit code is 4 although the record exists, and a wrapper that retries on exit code 4 can append the record twice. Check the log before retrying.
- Names: the writer refuses the zero-width joiner and non-joiner (U+200D, U+200C) and variation selectors, so family and other joined emoji, emoji that need U+FE0F (the red heart, keycaps) and Persian or Indic names that need a joiner cannot be used as actor or tool names. Flags, skin tones, CJK, Hangul, Arabic, Hebrew and combining marks are fine.
- On Windows, `append` to a path name that the checker accepts but Windows cannot create (for example a name with `*`, `?`, `<`, `>`, `|` or a quotation mark) takes about 5 seconds before it reports `output_error`, because a failure to create the lock file of that kind is retried like lock contention. `verify` reports such a name at once.
- The lock wait of 5 seconds is fixed. A burst of many hundreds of simultaneous appends to one log can exceed it and report `lock_timeout` for the last ones.
- Locking and flushing rely on the filesystem. Behaviour on network drives and unusual filesystems is not tested, and writing an output file without `--force` uses `fs.link`, which needs a filesystem with hard links (not FAT, some network shares). Keep backups.
- A zero-byte file is not a log: `summary`, `show` and `export` fail with `log_corrupt`, `verify` reports `bad_header`, and `append` starts a new log in it.
- Unicode versions. `append` refuses a name that holds an unassigned code point, and which code points are unassigned depends on the Unicode data of the Node.js that runs it (a newer Node.js assigns more). The writer is therefore strict by the Unicode data of the running Node.js, while the stored-record check is version independent: `verify` and the tail check of `append` (both through the record shape check) test stored names only with a fixed table of stable classes and never apply the unassigned rule. `show`, `summary` and `export` do not look at names with that table: they check the key set and the canonical form of every line and sanitize all output. The fixed table holds only explicit stable classes, and every entry is a class that the writer rejects on every Node.js: ASCII and C1 controls (U+0000 to U+001F, U+007F to U+009F), U+00A0, soft hyphen U+00AD, U+034F, the Arabic and Syriac format characters U+0600 to U+0605, U+061C, U+06DD, U+070F, U+0890, U+0891, U+08E2, the fillers U+115F, U+1160, U+3164, U+FFA0, U+1680, U+17B4, U+17B5, U+180B to U+180F, the space separators and format characters U+2000 to U+200F, the line and paragraph separators and bidirectional controls U+2028 to U+202F, U+205F to U+206F, U+2800, U+3000, surrogates and the BMP private-use area (U+D800 to U+F8FF), U+FDD0 to U+FDEF, variation selectors U+FE00 to U+FE0F, U+FEFF, U+FFF0 to U+FFFC, the noncharacters U+FFFE and U+FFFF of every plane, U+110BD, U+110CD, U+13430 to U+1343F, U+1BCA0 to U+1BCA3, U+1D173 to U+1D17A, U+E0000 to U+E0FFF and planes 15 and 16. It is a subset of what the writer rejects: all visible punctuation (hyphens, dashes, curly quotes, bullets, ellipsis, per mille and prime signs, U+2010 to U+2027 and U+2030 to U+205E), symbols, letters, marks and numbers that the writer accepts are outside it, which a test checks over every code point. A log written on a newer Node.js verifies on an older one; an older Node.js may still refuse to write a name that a newer one accepts. The terminal and CSV output replacement of unassigned code points does follow the running Node.js, so the same record can print differently on different versions. CSV cells are sanitized lossily: a literal backslash-u in a cell cannot be told from the escape that replaces an invisible character.
- Look-alike names: `append` refuses the literal name `(other)` (so it cannot merge with the summary overflow bucket) and a name that starts or ends with a space. Readers do not apply these two rules, so a forged log may contain such names; `summary --details` then counts a stored `(other)` together with the overflow bucket.
- Display collisions: terminal output collapses names and object keys that differ only by replaced (invisible) characters into one entry, and only one of the counts is shown. JSON output and exports are exact. JSON output passes bidirectional and other format characters through raw by design (only DEL and C1 controls are escaped).
- `summary` never stores a name longer than 128 code points (it counts it under `(other)`), and the `summary --details` output is limited to 16 MiB; a forged log can make it fail with `limit_exceeded`.
- Parent directory components of a path are not checked. A log below a symlinked or junctioned directory is accepted.
- Paths with a colon (other than the drive letter of an absolute Windows path), names ending in a dot or space, and Windows device names are refused on every platform, even where the operating system would allow them.
- There is no network collection, central aggregation, trusted timestamping or user authentication.
- Only Node.js 20 or later is supported, and only the library entry point `joons-mcp-audit-trail` is a supported import.
